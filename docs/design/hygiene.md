# Repository hygiene

Cruft is not a one-off. A loop that ships an item every few hours produces stale docs, orphaned scripts and dead exports faster than any human cleans them, and the repository is a public MIT artifact — what a newcomer reads first is `README.md`, `docs/`, and the top-level directory listing. So hygiene gets what every other area gets: a rule, a guard, and a cadence.

The audit this section is built on ran on `main` at `6b41b52`, 417 tracked files, on 2026-08-27. Its findings are recorded once in §13.6 so no future tick re-derives them by hand.

The hard part is not finding cruft. It is making deletion safe for an agent that cannot ask before it acts.

### 13.1 The deletion rule

Four clauses, binding on every tick, not only `hyg-*` ticks.

1. **Evidence or no deletion.** No tick removes a tracked file, an exported symbol, or a declared dependency without a committed evidence report generated by `scripts/repo-refs.mjs --evidence docs/hygiene/<item-id>-evidence.md`. The report names the scan set, the resolver rules it applied, and the zero-hit result per removed thing. A grep the reviewer cannot re-run is not evidence.
2. **Deleting lands Tier C.** §0.6's Tier-C list gains an eighth entry, worded to be classifiable from the diff alone:

   > 8. Any diff that deletes a tracked file, removes an exported symbol, or removes a line from `package.json`'s `dependencies`/`devDependencies`. A pure rename — `git diff --name-status` reporting `R100` with no content change — is **not** a deletion under this rule.

   §0.6 rule 6 is amended in the same splice to read `Dockerfile` / `docker-compose.yml` / **`.dockerignore`**, because what ships in the image is the same class of risk as how it is built.

   **These are two prose edits to a rail, so the owner applies them** (§17 q34). The loop must never edit its own tick protocol. Until they are applied the classifier does not know the rule, so **every deleting item carries the requirement in its own acceptance**: `hyg-05`, `hyg-07` and `hyg-09` open a PR and set `status: review` regardless of what `scripts/landing-tier.mjs` says. `hyg-01` teaches the classifier both rules so the belt and the braces agree.
3. **SUSPECT becomes a question, never a deletion.** Where the audit could not prove a file dead — or proved it unreferenced but plausibly still wanted — the disposition is a numbered question under §17 carrying a **keep** assumption, and a row in the baseline that stops it growing. Unreferenced is not the same as worthless, and an agent is exactly the wrong actor to decide which.
4. **Reproducibility tooling is archived, not deleted.** The capture rig is proven unreferenced and two of its scripts are broken after a clean install — and it is also what produced shipped artifacts (the README stills, `docs/assets/before-after-fix.png`, the OG card), while `make-capture-db.mjs` encodes the capture privacy rules. Deleting it destroys the ability to regenerate work that is live. It moves to `scripts/media/` with a guide (`hyg-09`); whether any of it is eventually deleted is §17 q29, not a tick's judgement.

**Never in scope for any hygiene deletion, at any time:** `agents/` and `skills/` (runtime data read by `src/lib/bootstrap.ts:37,80` and `prisma/seed-demo.ts`), anything under `servo_design_system/` (§0.5 and §17 q19 make it design truth), `tests/fixtures/`, `prisma/migrations/`, `docs/hygiene/` and any evidence file, and `prisma/*.db*` (db-10 deleted the last of them together with their ignore rules; loop-guard rail 4 refuses one coming back). The scanner carries this list as data, not as a convention a tick can reason around.

### 13.2 What counts as evidence

`scripts/repo-refs.mjs` is the one reference scanner. Node builtins only, pure functions plus a CLI, in the same shape as `loop-guard.mjs` and `spec-lint.mjs`. The traps it must encode, because each was hit by hand during the audit:

- **`.claude/` holds two full worktree copies.** Any scan that does not exclude it reports every file as referenced. Excluded, with `node_modules/`, `.next/`, `.git/`, `.spec-build/`, `package-lock.json` and `prisma/*.db*`.
- **`spec.md` names paths it plans to create.** Excluded as a *referencing* source. The cost is that a file only `spec.md` mentions reads as unreferenced — correct today, wrong the day a tick creates it, and absorbed by the baseline. A tick must never delete on that signal alone.
- **Dynamic imports and barrel files are reported, never guessed.** Today there is exactly one dynamic import (`src/lib/screenshot.ts:56`, importing `puppeteer-core`) and no barrel file in `src/components/common/` (was `legacy/` until hyg-06) or `src/components/ui/`. An unresolved dynamic import makes the run report `INDETERMINATE` for that target — never `unreferenced`.
- **Dependencies are part of the reference graph.** Declared-and-unused (`gifenc`) and used-but-undeclared (`sharp` in `make-before-after.mjs`, `ffmpeg-static` in `record-hero.mjs` — the latter absent from `package-lock.json` entirely, so it cannot work after `npm ci`) are both findings.

### 13.3 The guard — extend the claims linter, do not add a second one

| check | where it lives | catches |
|---|---|---|
| banned phrases | `scripts/claims-audit.mjs` (`reb-07`, exists) | copy that states or implies something untrue |
| **dead paths** | the **same** script, same `claims:audit` npm script, same CI step (`hyg-03`) | a document asserting a file exists when it does not |
| **unreferenced files and dependencies** | `scripts/repo-refs.mjs --check` against a baseline (`hyg-04`) | files and packages nothing points at |

The split is on kind, not convenience. `README.md` pointing at `prisma/seed.ts`, `docs/history/CONTRACT.md` pointing at `src/lib/ai/tools.ts` and `tailwind.config.ts`, and `docs/PORTING-LEDGER.md` pointing at `THIRD-PARTY.md` are all **false claims about the repository**, so they belong to the claims linter and its one machine-readable exemption block in `docs/POSITIONING.md`. There is no second banned-phrases canon and no second CI claims step. An orphaned file makes no claim about anything, so it belongs to the graph tool.

Two things this area deliberately does **not** add: **ESLint, Prettier or Biome** — three devDependencies and a first run that will not be clean is a decision with its own tradeoffs, not a side effect of a cleanup pass (§17 q33); and **a second colour lint** — `scripts/dev/color-audit.mjs` is a documented invariant nothing runs (`docs/DESIGN.md:8,60`), and the right fix is for `ds-01` to run it in the same step as `no-hex-lint.mjs`, not for hygiene to invent a third script.

Three refusals, written down so no tick re-proposes them:

- **`spec.md` never leaves the repository root.** §0.1's launch command, §0.2 step 1 and `.spec-build/` all name it there. A tidier `docs/spec/control-plane.md` buys nothing and breaks the loop's own protocol.
- **The loop's tooling never leaves `scripts/` root.** §0.2 step 2, §0.6 and six backlog items name `scripts/loop-guard.mjs`, `spec-lint.mjs`, `migration-guard.mjs`, `permissions-guard.mjs`, `landing-tier.mjs` and `policy-guard.mjs` by exact path.
- **`docs/PORTING-LEDGER.md` stays where it is.** `reb-03`, `db-10` and §16 name that path in acceptance criteria and in the claims-audit `sqlite` exemption. It gains a dated header (`hyg-02`) and its entries are never rewritten; only its rules block is live. That heading is what "the marked history section" in those three places refers to — nothing writes it today, so if `reb-03` lands first it must use the heading name `hyg-02` creates.

`servo_design_system/` keeps its name and its place (§17 q19). What it gets is one clause in the README structure block saying it is design truth the loop reads, not application code the build imports — which is the actual source of the confusion.

### 13.5 The recurring chore

`hyg-audit-NN` is a standing item. It re-runs the audit, writes a dated report, and turns findings into **questions**. It deletes nothing, moves nothing, and **appends no backlog items on its own authority** — there is no precedent in this file for the loop writing its own work orders (`loop-07`'s mining ticks write docs only).

**Cadence.** §0.2 step 4 gains one sentence, parallel to the mining sentence already there:

> Before the normal pick, if the Changelog holds twenty or more rows since the most recent `hyg-audit-*` row — or since the first row, if there is none — and no item is in `review`, the loop picks the due `hyg-audit-NN` item instead of the first unblocked `todo`, runs it once, and resumes normal order.

Twenty rows is roughly four days of ticks. This is a rail edit with no owning item, so the owner splices it (§17 q34). If the owner declines it, `hyg-audit-NN` still works — it simply runs only when the backlog has no other unblocked item, the same slot as a mining tick.

**Re-arming.** The completing tick sets `hyg-audit-NN` to `done` and appends `hyg-audit-<NN+1>` — identical acceptance, `status: todo`, `date: -` — at the **end** of §14. Append-only, no forward reference, ids never collide, `spec-lint` stays green with no change to its rules.

**Output discipline.** The audit tick writes exactly three things: `docs/hygiene/audit-<date>.md`, baseline **additions** for files that are legitimately new-and-unreferenced (each with a reason and the id or §17 question that owns it), and `spec.md` — where every proposed removal becomes a numbered question under §17 with a keep assumption, for the owner to promote into an item. The tick is docs-and-spec only, so it lands Tier A on green, and a clean audit still re-arms and still writes its changelog row.

### 13.7 Risks

1. **`.dockerignore` can silently ship a broken desk.** `syncSkills`/`syncAgentProfiles` return 0 on a missing directory. Mitigated by an in-image `ls` in `hyg-07` and by `tests/dockerignore.test.ts`, which fails offline when the rules regress. `docker build` pulls base images and runs `npm ci`, so the **offline test is the binding criterion** and the in-image `ls` is an owner-run proof recorded in the commit message.
2. **`ds-01` imports CSS from `servo_design_system/tokens/`**, so excluding that directory wholesale breaks `next build`. `hyg-07` depends on `ds-01` and carries an explicit `!servo_design_system/tokens` re-include.
3. **Two `formatDateTime` implementations with different output** (`src/lib/utils.ts:17`, dead; `src/components/admin/time.ts:21`, live, used by `ApprovalHistoryTable.tsx:13`). The deletion item names the file, not the symbol.
4. **`hyg-06` touches ~30 import lines** and can conflict with an unmerged UI branch. It runs after `hyg-05` so nothing is renamed and then deleted, and a conflict is resolved by rebasing, never by re-applying the rename by hand.
5. **A grep-based scanner has false negatives** — a path built from a template literal or an env var is invisible to it. Mitigated by the never-delete list and by clause 2: a human sees every deletion in a PR.
6. **Three relative-time implementations survive this phase.** `src/components/admin/time.ts` and `src/components/tickets/format.ts` differ only in their >30-day tail, so consolidating them changes what the Approvals history table prints. That is a behaviour item (§17 q32), not something smuggled into a cleanup tick.
7. **`.github/workflows/ci.yml`'s header comment** claims "SQLite means no services are needed" — false the moment `db-02` adds its `services:` block. `db-02` already rewrites it; adding `.github/workflows/ci.yml` to `db-10`'s file list would close the residue path completely, and is recommended as a one-line owner edit rather than done silently here.
